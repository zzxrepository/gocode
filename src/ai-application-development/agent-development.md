# 什么是 AI Agent

## 前言

Agent 是一个比大模型更早出现的概念。它描述的不是某一种模型，而是一类能够围绕目标与环境交互的实体或程序：获取信息、作出决策并执行动作。AI Agent 和 LLM Agent 都属于这个更大的范围。

本文先说明三个概念的边界，再重点介绍当前生成式 AI 应用中最常见的 **LLM Agent**。为简洁起见，后文在没有特别说明时，"Agent" 指的都是 LLM Agent，而不是所有广义 Agent。

## Agent、AI Agent 与 LLM Agent

三者是逐层收窄的关系：

```text
Agent（代理）
└── AI Agent（人工智能智能体）
    └── LLM Agent（大语言模型智能体）
```

### Agent：围绕目标感知、决策与行动

Agent 原意是“代理者、执行者”。在计算机领域，它是能够感知环境、基于目标作出决策并执行动作的实体或程序。经典人工智能教材《Artificial Intelligence: A Modern Approach》（AIMA）进一步强调“理性行动”：在已有信息和目标下，选择更可能达成目标的行动。[AIMA 作者的在线导读](https://aima.eecs.berkeley.edu/~russell/intro.html) 是理解这一视角的好起点。

广义 Agent 不必使用人工智能。例如，监控程序发现服务不可用后按固定规则重启服务，也可以被称为 Agent；它有输入、目标和动作，但没有机器学习或大模型能力。

### AI Agent：用 AI 方法完成决策的 Agent

AI Agent（人工智能智能体）是使用人工智能方法进行感知、判断、推理、规划或决策的 Agent。它可以采用规则与知识表示、机器学习、强化学习、计算机视觉等技术；游戏中的智能角色、强化学习控制器和机器人决策系统都可能属于这一类。

AI Agent 的关键不是“能聊天”，而是围绕目标持续形成闭环：

```text
感知环境 → 理解目标 → 决策或规划 → 执行动作 → 观察结果 → 调整下一步
```

### LLM Agent：以大语言模型为核心决策器

LLM Agent 是 AI Agent 的一种：它以大语言模型作为理解自然语言、推理和选择下一步的主要决策组件。在多模态任务中，这个核心也可能是多模态大模型（MLLM）。

模型本身只是模型，不会天然拥有业务事实、长期记忆或执行权限；这些能力来自模型外部的检索、存储、工具与运行时控制。因此，一个 LLM Agent 更准确的理解是：**以 LLM 为决策核心，结合规划、记忆、工具调用、行动和反馈循环组成的应用系统。**

在今天的生成式 AI / 大模型语境中，人们口头所说的“Agent”通常默认指 LLM Agent。本文也采用这一约定。

## LLM Agent 的概念架构

![LLM Agent 的感知、思考、规划、记忆、执行与反馈闭环](/assets/image/ai-agent-architecture.svg)

*图中展示的是 LLM Agent，而不是所有类型 Agent 的通用架构：大模型是决策核心，记忆与核心双向读写；任务主线由“环境 → 感知 → 思考与规划 → 执行 → 工具与环境”组成，执行结果再以反馈回到感知。本图为面向本文的重新绘制，结构参考 Lilian Weng 的 [LLM-powered Autonomous Agents](https://lilianweng.github.io/posts/2023-06-23-agent/)（2023）。*

这类架构中，图中央的 Agent 不是“一个大语言模型”的同义词，而是由模型和外围能力共同构成的系统。常见的四类能力是：

| 能力 | 作用 | 典型内容 |
| --- | --- | --- |
| Planning（规划） | 把目标转化为可执行的下一步 | 子任务拆解、路径选择、反思与修正 |
| Memory（记忆） | 保存和取回任务所需的信息 | 当前任务状态、长期知识、用户偏好 |
| Tools（工具） | 访问外部信息或系统能力 | 搜索、数据库、日历、代码执行、业务 API |
| Action（行动） | 将决策落实为对环境的操作 | 调用工具、发送消息、创建工单、提交申请 |

一个典型执行过程如下：接收用户目标，读取当前上下文和必要记忆，由 LLM 决定下一步；如果需要外部事实或操作，就选择并调用工具；工具结果回到上下文后，系统继续判断、规划或反思，直到任务完成、需要澄清、达到资源上限，或遇到必须由人审批的动作。

对用户而言，普通聊天机器人主要负责“回答”；LLM Agent 的目标是“把事情推进到可以交付的状态”。例如，“为缺货图书创建补货申请”不仅需要生成建议，还可能需要查询库存、比对供应商报价、整理方案，并在获得授权后调用采购系统创建申请。

这不代表 Agent 可以脱离人和程序独立工作。它始终运行在开发者给定的权限、工具、预算、超时和安全规则之内；所谓“自主”，是指它能在这些边界内选择下一步，而不是每一步都由人或固定代码预先写死。

## 从经典 Agent 到 LLM Agent

LLM Agent 沿用了经典 Agent 的“感知—决策—行动”框架，只是把感知和决策换成了更适合软件系统的实现：

| 经典智能体概念 | LLM Agent 中常见的实现 |
| --- | --- |
| 环境 | 用户消息、网页、数据库、文件、业务系统、工具返回结果 |
| 感知 | 读取文本、检索知识、接收 API/工具执行结果 |
| 目标 | 用户指令、工单目标、业务规则和停止条件 |
| 决策 | 大模型根据上下文选择回答、调用工具、请求澄清或结束 |
| 行动 | 调用搜索、数据库、代码执行、发消息、创建工单等工具 |

因此，Agent 的关键不在于“用了大模型”，而在于它形成了**目标 → 获取信息 → 选择动作 → 观察结果 → 再选择**的闭环。

## 它和聊天机器人、工作流有什么区别

这三类系统没有高下之分，差别在于“下一步由谁决定”。

| 形态 | 下一步如何决定 | 图书业务中的例子 | 适合什么问题 |
| --- | --- | --- | --- |
| 聊天机器人 | 用户继续提问 | 回答“这本书是否有库存？” | 单次问答、解释、写作 |
| 固定工作流 | 开发者预先编排 | 校验 ISBN → 查库存 → 创建订单 | 步骤稳定、规则明确、需要高确定性 |
| Agent | 模型在受控范围内选择 | 先查库存；缺货时再查替代书和到货时间；信息不足时追问用户 | 输入非结构化、路径不固定、需要在工具之间判断 |

例如，“每天同步供应商的价格表”通常应使用定时工作流；“阅读一批格式不同的供应商邮件，找出涨价商品并生成待审核的采购建议”更适合 Agent。实践中常见的可靠方案不是二选一，而是**用确定性工作流包住一个受限 Agent**：工作流负责权限、审核和提交，Agent 负责理解非结构化内容与提出建议。

## 一个 Agent 的最小闭环

现代工程实践中，不必把 Agent 固定套进“四大件”的口号。OpenAI 的实践指南将其最基础的组成概括为模型、工具和指令；真正可运行的系统还需要一个调度循环，以及生产环境的边界控制。[OpenAI 的构建指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/) 也强调，应先从尽可能简单的系统开始。

```text
用户目标
   ↓
指令 + 当前状态 ──→ 模型决定下一步
                         ├─ 直接给出结果
                         ├─ 请求补充信息
                         └─ 选择一个工具
                                   ↓
                            工具执行并返回事实
                                   ↓
                             更新状态，继续循环
```

可以把常见模块理解为下面几类，而不是把它们都当成每个 Agent 的必选项：

| 模块 | 作用 | 是否一定需要 |
| --- | --- | --- |
| 模型 | 理解自然语言、基于上下文选择下一步 | 对 LLM Agent 通常需要 |
| 指令与目标 | 规定任务、规则、输出格式、何时停止 | 必须有 |
| 工具 | 读取外部事实或改变外部系统 | 只回答问题时可以没有；要“办事”时需要 |
| 运行循环 | 把工具结果交还给模型，直到完成、失败或超限 | 多步 Agent 需要 |
| 状态与记忆 | 保存本次任务进展，或跨任务保留经授权的信息 | 按任务需要 |
| 规划 | 先列计划、分解任务、选择路线 | 复杂任务常用，简单任务未必需要 |
| Guardrails 与评估 | 权限、校验、预算、审计、质量测试 | 生产环境必须认真设计 |

“LLM 是大脑”是便于入门的比喻，但不要按字面理解。模型不会天然记住业务事实，也不会天然拥有权限；事实来自检索和工具，记忆来自外部存储，动作权限来自系统设计。

## 工具调用：从会说到能做

工具是 Agent 接触外部世界的接口。一个工具通常有名称、用途说明、参数 schema 和执行实现。例如：

```text
get_inventory(isbn)              # 查询库存，只读
search_supplier_quotes(isbn)     # 查询供应商报价，只读
create_purchase_request(items)   # 创建采购申请，会改变业务系统
```

模型并不是直接连接数据库。它先产生结构化的“工具调用请求”；应用程序验证工具名和参数、检查权限，然后才真正执行。执行结果再作为新的上下文交回给模型。这个区分很重要：**模型提出动作，不等于模型有权执行动作。**

设计工具时应遵循几个简单但关键的原则：

- 工具职责单一、名称和参数清楚，避免一个“万能工具”暗中执行多种操作。
- 服务端再次校验参数和权限，不能相信模型生成的参数。
- 对发邮件、删除数据、付款、创建订单等有副作用的操作设置确认或人工审批。
- 给工具设置超时、重试策略、调用次数和金额/数据范围上限，并记录审计日志。
- 将工具返回的网页、邮件或文档视作不可信输入，不能让其中的文字覆盖系统指令。

## 规划与 ReAct：为什么 Agent 会反复行动

复杂目标常常不能靠一次工具调用完成。比如“为缺货图书准备补货方案”至少需要确认库存、在途数量、供应商报价和采购规则。Agent 可以先形成一个简短、可检查的任务计划，再逐步执行；也可以每拿到一个工具结果就重新判断下一步。

ReAct（Reason + Act）描述的正是这种交替：基于当前信息决定一个动作，观察动作结果，再据此调整后续行动。[ReAct 的原始研究介绍](https://research.google/blog/react-synergizing-reasoning-and-acting-in-language-models/) 展示了“推理帮助选择行动、行动带来新信息”的互补关系。

工程上不需要让系统无限思考。一个受控循环应有明确停止条件，例如任务已完成、信息不足需追问、工具失败、达到最大步数、超出时间预算，或遇到需要人工授权的动作：

```go
// 伪代码：模型负责提出下一步，程序负责执行与约束。
for step := 0; step < maxSteps; step++ {
	decision := model.Decide(state, allowedTools)

	if decision.IsFinalAnswer() {
		return decision.Answer
	}
	if decision.NeedsHumanApproval() {
		return askHumanToApprove(decision)
	}

	// 服务端必须校验参数、权限和预算，不能直接相信模型输出。
	result, err := toolRunner.Execute(decision.ToolCall)
	state.AddObservation(result, err)
}
return "未能在限定步骤内完成，需要人工处理"
```

显式规划有帮助，但不是越复杂越好。对于路径固定的任务，普通代码或工作流通常更可靠、更便宜；对于需要模型判断路径的任务，先从少量工具和较小的最大步数开始。

## 记忆：不是把所有聊天记录永久塞进提示词

“记忆”至少有三种不同含义：

| 类型 | 保存什么 | 图书采购 Agent 的例子 |
| --- | --- | --- |
| 上下文 / 短期状态 | 当前任务中刚发生的对话、工具结果、已完成步骤 | 已查询的库存和报价 |
| 长期知识 | 文档、规则、历史案例，可按需检索 | 采购制度、供应商目录 |
| 用户偏好 | 经用户同意后保存的稳定偏好 | 默认仓库、常用审批人 |

上下文窗口不是可靠数据库：它有限、会增加成本，也可能混入无关或敏感内容。长期知识通常存放在数据库、文档库或向量检索系统中，需要时检索相关片段；用户偏好则应有明确的数据生命周期、删除机制和访问控制。

记忆也不等于模型训练。把某条信息写入记忆库，只是让后续任务有机会检索到它，并没有改变模型的参数。

## Agent 的边界：自主不等于不受控制

Agent 的风险主要不来自“回答错一句话”，而来自它能读写真实系统。可靠性设计应围绕以下边界展开：

| 边界 | 要回答的问题 | 常见做法 |
| --- | --- | --- |
| 权限 | 它能访问哪些数据、调用哪些操作？ | 最小权限、工具 allowlist、按用户身份鉴权 |
| 动作 | 哪些操作可以自动执行？ | 只读自动化；写操作确认或审批 |
| 资源 | 最多调用几次、运行多久、花多少钱？ | 最大步数、超时、并发和成本预算 |
| 输入 | 工具返回内容是否可信？ | 标记不可信数据、隔离指令、参数校验 |
| 可观测性 | 出错时如何还原发生了什么？ | trace、工具调用日志、输入输出审计与评估集 |
| 兜底 | 做不下去时怎么办？ | 请求澄清、转人工、返回可解释的失败状态 |

多 Agent 并不天然更强。把任务拆给多个角色会增加通信、状态一致性、调试和成本问题；只有当角色边界真的清晰、单个 Agent 的上下文或工具选择已经难以管理时，才值得引入协调器或多个专用 Agent。Anthropic 的工程指南也建议先选择最简单可行的模式，再逐步增加自治与编排复杂度。[Building Effective AI Agents](https://www.anthropic.com/engineering/building-effective-agents)

## 什么时候应该使用 Agent

优先考虑 Agent 的场景通常同时具备以下特征：输入是自然语言、文档或网页等非结构化信息；任务路径会随信息变化；系统需要借助多个工具获取事实或推进工作；人愿意接受一定的非确定性，并能为高风险动作设置审核。

不适合的典型场景包括：

- 规则简单稳定，例如按固定公式计算运费。
- 步骤明确且必须完全可复现，例如支付扣款、数据库迁移。
- 没有可信的数据或工具可用，只能让模型猜测事实。
- 失败代价很高，却没有审批、审计和回滚机制。

一个实用的判断问题是：**如果把每一步都写成确定性代码并不困难，就先不要引入 Agent。**先用普通 API、检索、工作流解决问题；只有当“理解输入和选择路径”真正成为瓶颈时，再让模型承担这部分决策。

## 总结

Agent、AI Agent 与 LLM Agent 的关系是逐层收窄的：Agent 关注“围绕目标感知、决策与行动”；AI Agent 用 AI 方法完成其中的决策；LLM Agent 则以大语言模型作为主要决策组件。当前大模型应用中常被简称为“Agent”的，通常就是最后这一类。

LLM Agent 不是单一模型功能，而是一种系统形态：它围绕目标运行，在受控边界内获取信息、选择动作、观察结果并继续推进任务。大模型让系统更擅长理解语言和选择路径；工具让它接触真实数据与业务系统；记忆和规划则是在任务复杂时可加入的能力。

真正决定一个 Agent 是否可用的，往往不是它能否写出漂亮回答，而是工具是否可靠、权限是否收敛、停止条件是否明确、失败是否可追踪，以及高风险动作是否保留给人来确认。
